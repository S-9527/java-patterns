# checkout-facade — 门面 + 中介者

## 场景

一次结算要牵动五个模块：库存、定价、风控、支付、通知。步骤有严格依赖，而且失败要回滚。

## 意图

两个模式，**动机完全不同**，经常一起出现：

- **门面**（Facade）—— **客户端视角**的简化："调用方不该知道要调五个服务"
- **中介者**（Mediator）—— **模块间视角**的解耦："这五个模块不该互相认识"

| | 门面 | 中介者 |
|---|---|---|
| 站在谁 | 客户端视角 | 模块间视角 |
| 解决什么 | 调用方要知道调哪些 | 模块之间不该互相认识 |
| 典型实现 | 一个门面方法包住一串操作 | 所有模块只和一个协调者说话 |
| 不做会怎样 | 调用方到处写编排 | 网状依赖，加流程要改 N 个模块 |
| 能单独要吗 | 能 | 能（但通常配合门面一起上） |

**只做门面不做中介者** → 模块间网状依赖依然存在。
**只做中介者不做门面** → 调用方仍要知道编排顺序。

## 类清单

| 类 | 角色 |
|---|---|
| `CheckoutFacade` | 门面，一个 `checkout(draft, channel)` 入口 |
| `CheckoutMediator` | 中介者，编排五个步骤 + 补偿逻辑 |
| `CheckoutContext` | **有界可变**的结算上下文 + sealed `Result` |
| `Services` | 五个下游服务，包私有静态嵌套类 |
| `CartDraft` | 购物车 |

## 编排顺序是有依赖的

```
定价 → 风控 → 扣库存 → 收款 → 通知
```

不是随便排的：

1. **定价** —— 风控要看金额，必须先算出来
2. **风控** —— 没过风控就不该占库存
3. **扣库存** —— 占了才能去收款
4. **收款** —— 收不回来要还库存

`CheckoutFacadeTest.riskBlocksBeforeStockIsTaken` 专门锁住第 2 条：

```java
assertFalse(names.contains("库存"), "库存步骤根本没被执行");
assertEquals(stockBefore, facade.stockSnapshot(), "风控没过就返回了，库存一行没动");
```

## 补偿逻辑属于中介者

支付失败要归还库存。这段逻辑写在 `CheckoutMediator.settle` 里：

```java
var payError = payment.charge(ctx, channel);
if (payError != null) {
    ctx.record("回滚", "支付失败，归还库存");
    inventory.release(ctx);
    notification.notify(ctx, false, payError);
    return ctx.fail(payError);
}
```

`paymentFailureRollsBackStock` 断言库存前后一致。

## 有界可变的上下文

`CheckoutContext` 是**可变**的 —— 和 `order-state` 场景里"状态是不可变 record 组件"
的取舍正好相反。

五个服务要往里写各自的结论（库存扣了多少、风控过没过、付了多少钱）。
如果每步都返回新对象，就得在中介者里手工搬运十几条数据。

这是**有界可变的典型形态**：只在结算线程内使用，不跨线程、不共享。

## 测试点（12 条）

- 正常结算：五步顺序正确、金额正确
- **风控拦截时不占库存**（编排依赖）
- 库存不足整单失败，不部分扣减
- **支付失败回滚库存**（补偿逻辑）
- 轨迹完整可回溯 / 轨迹不可变
- 门面暴露中介者（精细编排可绕过门面）
- 门面不共享状态
- 上下文有界可变
- `Result` 是 sealed 的两种结局
- 库存跨订单持续扣减
- **中介者编排无环**：`定价 < 风控 < 库存 < 支付`

## 什么时候不该用它

**1. 只有一个调用方时。** 门面是给"很多调用方"省事的。单一调用方加门面，
只是多了一层无意义的间接。

**2. 中介者服务数超过十几个时。** 编排逻辑集中到一个类，几十个服务时它会变成几千行。
而且加一种新流程（预售锁单）可能要改它。

**3. 步骤之间是"通知"而不是"需要结果"时。** 如果流程是"下单后发短信、加积分、通知风控"
——各步骤互不关心对方的结果，那不该用中介者，应该用**事件**。
**这正是中介者和观察者的分界**：中介者里每一步都要问下一步要结果，事件里各走各的。

**4. 流程顺序经常变时。** 中介者把顺序写死在 `settle` 里。
如果结算顺序需要按地区配置，那说明它不是一个固定流程，模板方法或策略更合适（见 `pipeline`）。

## GoF 原文自己就说中介者"不常被用到"

它的代价是真实的：

- 编排集中到一个类，服务多时它会变成几千行
- 加一种新流程可能要改它
- 调试时堆栈全在一个类里，看不出是谁在驱动

**真正让模块松耦合的往往是事件，不是中介者** —— 见 `domain-events` 场景。

中介者合适的前提：**步骤多、顺序固定、且每一步都需要前一步的输出**。
本项目只有 5 个服务，真项目到 50 个就该考虑换成事件驱动了。
